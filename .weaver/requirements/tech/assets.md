# Assets

## assets
- **Where:** listing, copying in, renaming and deleting assets, the asset rules, tag recognition, the block appended to messages, its removal from replayed text and the sentences of instructions live in `weaver-core` (sync `std` I/O, pure functions where possible); `src-tauri` exposes them as Tauri commands run in `spawn_blocking`. The UI never touches a file and still gets no `fs` plugin.
- **Asset list:** per open project, in backend memory only: the name and size of every asset (`requirements/rules#asset-view`), from one `read_dir` of `.weaver/assets/` and the metadata it returns, never opening a file. It is read when the project opens and again after each batch of watcher events under `.weaver/assets/`; a missing folder is an empty list. Each change is sent to every window of the project as an `assets-changed` event with the project id, a generation number and the whole list; a command returns the current list to a window that starts. It is `workspace.ASSETS_CHANGED`.
- **Watching:** no new watcher. The project watcher (`requirements/tech#project`) already sees `.weaver/assets/`; its events there go only to the asset list, batched 150 ms after the last one, and never reach the project picture, its rebuild, `project-changed` or `workspace.FILES_CHANGED`.
- **Message boxes:** one shared component serves the four boxes of `requirements/ui#assets`. It keeps a native `textarea` for typing, caret, selection, undo and accessibility; behind it a mirror layer with the same font, size, padding, border, wrapping and scroll draws the text with the recognised tags coloured, while the textarea's own text is transparent and its caret stays visible (`caret-color`). The mirror's scroll follows the textarea's on every scroll and resize. The caret position for the suggestion list is measured on the mirror. Tag recognition in the UI uses the same rules as the core, on the asset list of the last `assets-changed`.
  - **One geometry for both layers:** the box metrics (padding, border width, font family, size, line height, letter spacing, wrapping) are set in one place of the component and reach the textarea and the mirror alike. A caller can change them only through that place, for both layers at once; what a caller may pass to the textarea alone (background, border colour, focus ring, resize) never changes where a character sits. A metric passed to one layer only is a mistake the component does not allow, not a style to merge.
  - **Caret marker:** the marker the mirror uses to measure the caret for the suggestion list never adds a line-break opportunity nor any width: with the list open or closed, the mirror wraps every line at the same characters as the textarea.
  - **Composition:** while a composition of the input method is in progress (`isComposing`), Enter and Tab are left to the textarea: no box sends, picks a suggestion or moves the focus on them.
- **Sending messages:** the backend commands that send a message in Chat, in a job's conversation and in an Ask more conversation recognise the tags against the asset list at that moment and append the block of `requirements/rules#assets` to the text that goes to omp as one ACP text block, after the developer's text (and, for the first Ask more message, after `ask::first_prompt`). The live `Developer` entry of the conversation keeps only the developer's text.
- **Replay:** when a conversation is rebuilt from omp's `user_message_chunk` replay, the developer's text is the replayed text without the appended block: the cut is at the last occurrence of the block's head line, only when every line after it is a sentence of that block. The same cut applies inside `ask::shown_message`.
- **Requests:** at `developer.SEND_REQUEST`, and at `agent.SEND_REQUEST` with the text Chat's agent gave, the backend reads the request text once, as it does to check that it is not empty, recognises the tags against the asset list at that moment, and gives the design or setup job the list of tagged asset names. The job keeps it in memory with its other fields until its instruction is sent; it is never written into the request file nor into the job registry, since a job that has not sent its instruction never resumes.

## asset-view
- **Commands:** they take asset names, never paths; the backend builds `.weaver/assets/<name>` after checking the name with the rules of `requirements/rules#asset-view`, and refuses any name with a separator. The only absolute paths are the sources of a drop from outside, as Tauri reports them.
- **Drops from outside:** the Assets view listens with `getCurrentWebview().onDragDropEvent` only while it is shown, as the File view and the request editor do (`requirements/tech#file-view`); the whole view is the target. A drop sends the absolute paths to one copy command, in `spawn_blocking`; a window holds at most one running copy and the command refuses a second with the reason. Every refusal is checked for every dropped file before anything is written. Files are read with `symlink_metadata`, never following a link. The command creates `.weaver/assets/` (and only it) when missing, each file with `create_new` and its bytes copied, never replacing anything; it records each file it created and, on a failure part way, removes them all. It returns the names copied and those larger than the size limit. A drop whose paths are all inside the canonical `.weaver/assets/` of the same project returns at once, changing nothing.
- **Rename:** one `rename` inside `.weaver/assets/` that never replaces an existing file, with the same primitive as the File view's rename (`requirements/tech#file-view`).
- **Delete:** with the `trash` crate, one asset at a time; the result lists the names the trash refused with their reasons.
- **Drag out:** the `drag` crate (CrabNebula, 2.x), called from the backend, never `tauri-plugin-drag`, because that plugin lets the webview name any absolute path. The UI uses pointer events as the File view's rows do (`pointerdown` with the primary button, the drag starting past 4 px, no HTML5 drag and drop API) and then calls one command with the asset names; the backend resolves their canonical paths inside `.weaver/assets/`, refuses any that is not an asset, and starts `drag::start_drag` on the main thread for that window (its GTK window on Linux) with `DragItem::Files`, `Options { mode: DragMode::Copy, .. }` and a preview image bundled with the app. The result (dropped or cancelled) changes nothing.
- **State:** per project window, in UI memory only: the selection and the grid's scroll. Nothing of the view is written to disk.
