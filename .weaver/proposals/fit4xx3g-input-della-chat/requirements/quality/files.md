# Files

## file-view

- **Performance:** while the File view is closed, Weaver reads no folder of the code and watches nothing outside `.weaver/` but the project root's own watch for `.weaver`. Showing the view reads only the root; expanding reads only that folder. No recursive read, index or search, ever, except reading a folder dropped from outside once to copy it in; a listing never opens a file. Expanding a folder starts at most one `git check-ignore`; nothing else of the view starts a process. A copy in never blocks the UI or the other commands of the view.
- **Reliability:** a copy in never replaces an entry, never changes the dropped originals, and never leaves part of a drop in the project.
- **Release:** 10 s after the view stops being shown, no watch and no listing of the code is left in memory; tested with an injected clock.
- **Tests:** listing (`.git` left out, ignored entries, dot names, no git), the watches added and dropped on expand, collapse, release and window close, the refusals of `requirements/rules#file-view`, rename and move never replacing an entry, deletion to the trash and its refusal, all against temporary folders with injected watcher timing; copy in against temporary folders: files, nested folders, symbolic links kept as links, permission bits, every refusal (inside the project, name taken including case, two dropped entries with one name, `.weaver/`, a second copy while one runs) and the removal of what was copied after a failure injected part way. In Vitest: the tree, its context menu, `F2`, `Delete`, `Move to…` and the leave dialog with their keyboard paths and accessible names; row dragging with pointer events (threshold, highlight, refused targets, `Esc`, `pointercancel`, the 1 s expand with fake timers, edge scrolling); drops from outside by emitting the Tauri drag-drop events (`enter`, `over`, `drop`, `leave`) through a mocked webview, with the progress toast, the refusal and failure toasts and the expand and selection after success. No tree test fires HTML5 drag events, so the tests exercise the events the app really receives. A Rust test checks that the project and welcome windows are built with Tauri's drag-drop handler on, and that `tauri.conf.json` does not turn it off.

## file-tab

- **Performance:** opening a file reads it once, an image included; an image tab reads its file again only after a change of its own watch; a grammar loads only with the first file of its kind; closing a tab frees its editor, text, image and watch at once. Typing starts no process and no disk work, and in an SVG tab draws nothing until the drawing is shown.
- **Reliability:** a save writes only when the file on disk still has the hash the tab read, except `Overwrite` and `Keep mine`; it never changes a byte the developer did not change, its line endings, its byte order mark or its permissions.
- **Logs:** never a file's content, an image's bytes or its `data:` URL; paths are allowed.
- **Tests:** binary detection, image signatures for each format and the 10 MB image limit, the SVG name rule, the size limit, the line-ending choice and the tab limit as pure functions; saving files with LF, CRLF, mixed endings, a byte order mark, no final line break, the executable bit and through a symbolic link, against temporary folders on every system; the hash check, `Overwrite`, `Save again`, a failed write and the self-write rule; an image read again after a change, turning binary, deleted and back; tabs, bars, dialogs, the image view (fitted and actual size by click and keyboard, an image that cannot be drawn), the SVG `Code` / `Preview` switch keeping the undo history, and shortcuts (`Cmd/Ctrl+S`, `Cmd/Ctrl+W`, `Ctrl+Tab`) in Vitest with their keyboard paths and accessible names.

## file-lock

- **Reliability:** a lock never outlives its tool's end, its conversation's turn, its omp process, its job or its conversation.
- **Tests:** with the scripted fake ACP agent: tools with and without `locations`, several tools on one file, tools of two conversations, end by `completed`, `failed`, turn end, exit, job end, cleared General and closed Ask more, updates replayed while a session loads, a move with its destination, a deletion, paths outside the root and on Windows.

## assets

- **Performance:** of `.weaver/assets/` Weaver reads only names, kinds and sizes, with one `read_dir` and the metadata it gives; it opens an asset only to copy it in. No asset event rebuilds the project picture. Recognising tags while the developer types starts no process and no disk work: it uses the names the UI already holds. A copy in never blocks the UI or the other commands of the window.
- **Reliability:** a copy in never replaces an asset, never changes the dropped originals and never leaves part of a drop; a drag out never moves or changes an asset; a rename never replaces another asset.
- **Logs:** never an asset's content or a message's text; asset names and paths are allowed.
- **Tests:**
  - In `weaver-core`, as pure functions: tag recognition (longest name, names with spaces, case, the characters allowed before and after, `@` without a match, the same asset tagged twice, order of first appearance), the block appended to a message and its removal from replayed text, the sentences added to a design or setup instruction, asset names, the size limit at exactly 10 MB and one byte above.
  - Against temporary folders: listing (dot names left out, folders and links left out), copy in of files, every refusal of `requirements/rules#asset-view` (folder, link, dot name, name taken including case, two dropped files with one name, a second copy while one runs), a drop of the project's own assets ignored, the removal of what was copied after a failure injected part way, the folder created on the first copy, rename never replacing, deletion to the trash with one refusal among several.
  - In Vitest, with their keyboard paths: the grid, its selection (click, modifier clicks, arrows, `Cmd/Ctrl+A`), the context menu, `F2`, `Delete` and its dialog, the size mark, the empty text; in each of the four message boxes the suggestion list (opening, filtering, order, Up, Down, Enter, Tab, Esc, Enter not sending while open) and the highlight following edits and asset changes.
  - In Vitest, for each of the four message boxes as its view renders it: the textarea and the mirror carry the same padding, border width, font family, size, line height and letter spacing; Enter and Tab during a composition neither send, nor pick a suggestion, nor move the focus. jsdom does no layout, so these tests check the styles both layers receive, not measured positions.

## notes-view

- **Performance:** TipTap loads only the first time the Notes view opens in a window. Typing starts no process and no disk work before the 500 ms pause; a write sends only the sheet's text. Each image is read once for display, and again only after a `notes-changed` names it. No notes event rebuilds the project picture. A copy of images never blocks the UI or the other commands of the window.
- **Reliability:** nothing the developer typed is lost: a waiting change is written when the editor loses the focus, the view is left, the window closes or the app quits. Content the editor does not support is written back byte for byte. A tick changes only that item's marker in the file. An image copy never replaces a file and never changes the originals. Weaver puts in the trash only images the developer removed, never any other file.
- **Logs:** never the sheet's text, an image's bytes or its `data:` URL; names and paths are allowed.
- **Tests:**
  - In `weaver-core`, as pure functions: image names (own name, invalid own name, date and time, taken names with `-2` and case), the accepted kinds by signature, the 10 MB limit at exactly 10 MB and one byte above, refused against left-out files.
  - Against temporary folders: the folder and its `.gitignore` created by the first write of the sheet and of an image, reading a missing sheet, atomic writing, CRLF read as LF, copies never replacing, links and folders left out, names refused with a separator, a leading `.` or `notes.md`, trash with one refusal among several, watcher events under `notes/` never reaching the picture and a self-write not sent.
  - In Vitest, with their keyboard paths: loading then saving gives back the same text for every element of `requirements/rules#notes-view` written as the editor writes it; unsupported blocks (raw HTML, a table, conflict markers, front matter) written back byte for byte; every Markdown shortcut of `requirements/ui#notes-view`; Enter continuing a checklist unticked and ending it on an empty item; Tab and Shift+Tab; ticking by click and by `Cmd/Ctrl+Enter`, changing only that marker; autosave timing and coalescing with fake timers; an outside change with and without a waiting write; the image placeholder for a missing image, a path elsewhere and an address; removed images collected through undo and redo, not through a reload, and trashed only when no longer named.
