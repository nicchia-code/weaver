# Ripiego GitHub per omp

Dietro alcuni proxy aziendali (per esempio Zscaler) l'installazione e l'aggiornamento di omp falliscono perché il canale di omp (`omp.sh` → build.stencil.so → Cloudflare R2) è bloccato come sito di file hosting, qualunque siano i certificati. Le release GitHub di omp (`can1357/oh-my-pi`) pubblicano lo stesso file e di solito passano. Quando questa Task è fatta, Weaver ripiega da solo sulle release GitHub sia per l'installazione sia per l'aggiornamento, su Windows, macOS e Linux (anche musl), x64 e arm64, senza nessuna impostazione nuova.

## Cosa dice il Model

- `omp-setup`: quando il canale di omp fallisce, Weaver ripiega sulla release GitHub, per installare e per aggiornare; un file da GitHub sostituisce omp solo se dimensione e checksum coincidono con quelli pubblicati da GitHub e se risponde una volta al suo posto. Ogni processo omp, **ogni download di omp** e ogni terminale di sistema avviato qui riceve System Certificates mentre è acceso.
- `developer.INSTALL_OMP` (da Missing → Installing): Weaver apre il terminale di sistema, che scarica ed esegue l'installer ufficiale; se fallisce, lo stesso terminale scarica omp per il sistema e il processore dello sviluppatore dall'ultima release GitHub, lo verifica, lo mette nella cartella dell'installer ufficiale e, su Windows, aggiunge quella cartella al `Path` dell'utente se manca. Lo sviluppatore vede tutto.
- Installing: alla fine il terminale lascia l'exit code dell'installazione dove Weaver lo legge; un terminale chiuso prima non lascia nulla. Weaver ricontrolla omp e quel codice ogni pochi secondi.
- `omp.INSTALL_FAILED` → Missing: omp non si trova e il codice è diverso da 0; Weaver mostra il codice con la sua causa (download bloccato, certificato non verificato, file da GitHub incompleto o alterato e non installato, omp da GitHub che non parte, ogni altra causa col testo di oggi).
- Updating: se l'aggiornamento di omp fallisce e omp è un file in una delle cartelle del suo installer, non installato da un package manager né scelto nelle impostazioni, Weaver scarica in background, senza terminale, l'ultima release GitHub solo se più nuova di omp, la verifica e la mette al posto di omp; su Windows il file in uso si sposta prima da parte, così i job in corso continuano. I job creati nel frattempo aspettano.
- `omp.UPDATE_ENDED` → Checking: l'aggiornamento di omp, o dopo il suo fallimento il download GitHub messo al suo posto, è finito bene.
- `omp.UPDATE_FAILED` → Ready (omp risponde con la versione minima e un modello usabile) o → Missing (omp resta più vecchio del minimo): si mostra il fallimento, quello del download GitHub quando è partito.

## Script dell'installer (`requirements/tech#omp-setup`, "Commands" e "GitHub download")

- Prima l'installer ufficiale come oggi (scaricato in un file temporaneo ed eseguito, mai in pipe). Con qualunque codice diverso da `0` lo stesso script stampa `The official installer failed (exit code <N>). Downloading omp from GitHub instead…` ed esegue il download GitHub: in `/bin/sh` su macOS e Linux, nel PowerShell padre su Windows. Poi scrive nel marcatore `<app local data>/omp-install/<nonce>.code` il codice dell'ultimo passo eseguito (`0` se l'installer ufficiale è riuscito) e cancella i file temporanei. `ompPath` non si scrive mai.
- Uno script per shell (POSIX `sh` + `curl`; Windows PowerShell 5.1 con `$ProgressPreference = 'SilentlyContinue'`), lo stesso testo per il terminale dell'installer e per l'aggiornamento in background. Il backend non ha un client HTTP proprio per questo.
- Asset: Windows `omp-windows-x64.exe`/`omp-windows-arm64.exe` da `PROCESSOR_ARCHITEW6432`, altrimenti `PROCESSOR_ARCHITECTURE`; macOS `omp-darwin-arm64` quando `sysctl -n hw.optional.arm64` stampa `1` (anche sotto Rosetta), altrimenti `omp-darwin-x64`; Linux `omp-linux-x64`/`omp-linux-arm64` da `uname -m`, con `linux-musl` al posto di `linux` se esiste `/etc/alpine-release` o `ldd --version` cita `musl`. Processore sconosciuto: codice `1` e `omp has no GitHub build for <system> <processor>`.
- Release da `https://api.github.com/repos/can1357/oh-my-pi/releases/latest` (`Accept: application/vnd.github+json`, 60 s): `tag_name` e, per l'asset col nome esatto, `browser_download_url`, `size` e `digest` (`sha256:` + 64 hex). Risposta non JSON della release, o senza asset o digest, vale come bloccata.
- Cartella: per l'installazione `PI_INSTALL_DIR` se impostata, altrimenti `%LOCALAPPDATA%\omp` o `~/.local/bin`, creata se manca; per l'aggiornamento la cartella del file omp trovato. File `omp.exe` su Windows, altrimenti `omp`.
- Download in `<folder>/.omp.download` (`.omp.download.exe` su Windows), redirect seguiti, 900 s (`curl -fL --connect-timeout 10 --max-time 900 -o`; `Invoke-WebRequest -UseBasicParsing -TimeoutSec 900 -OutFile`). Verifiche nell'ordine, ognuna cancella il file se fallisce: stato 200; dimensione uguale a `size`; SHA-256 uguale a `digest` (`sha256sum`, altrimenti `shasum -a 256`; `Get-FileHash -Algorithm SHA256`); `chmod 755` su macOS e Linux; spostamento al suo posto; `<folder>/<file> --version` con codice `0` entro 15 s.
- Sostituzione: su macOS e Linux lo spostamento rimpiazza il file. Su Windows un `omp.exe` esistente si rinomina prima `omp.exe.<unix seconds>.old`; se la verifica di versione fallisce, il file nuovo si cancella e il vecchio torna al suo nome. Ogni download cancella prima i file `omp.exe.*.old` cancellabili della sua cartella.
- PATH, solo per l'installazione: su Windows, se la cartella non è nel `Path` dell'utente (confronto senza maiuscole e senza `\` finale), `[Environment]::SetEnvironmentVariable('Path', '<user Path>;<folder>', 'User')`; su macOS e Linux, se non è in `PATH`, stampa `Add <folder> to your PATH to use omp in your own terminal.` senza toccare file della shell.
- Exit code: `0` installato; `90` bloccato (stato HTTP diverso da 200, pagina HTML o risposta che non è la release, connessione fallita o scaduta); `91` certificato (curl `60` o `77`, o errore PowerShell che è un errore di certificato di `requirements/rules#system-certificates` o contiene `trust relationship`); `92` dimensione o SHA-256 diversi; `93` l'omp messo al suo posto non risponde a `--version`; `94` release non più nuova della versione data (solo aggiornamento); `1` ogni altro fallimento. Ogni fallimento stampa il passo, l'indirizzo e lo stato HTTP o il messaggio dello strumento.
- Quoting: una sola funzione testata quota per la shell di destinazione; si inseriscono solo il path assoluto di omp, un provider della lista fissa, il path del bundle, il path del marcatore, e cartella e versione di omp per il download in background. Il repository, l'indirizzo dell'API e i nomi degli asset sono costanti di `weaver-core`; nessun file di progetto, nessuna variabile d'ambiente oltre `PI_INSTALL_DIR`, `LOCALAPPDATA`, le variabili del processore e quelle dei certificati, e nessun messaggio della UI sceglie cosa si scarica o dove. Mai `-k`/`--insecure` né `-SkipCertificateCheck`.
- Installing resta com'è: ricontrolli ogni 3 s; senza omp si legge il marcatore del nonce corrente, un codice diverso da `0` è `omp.INSTALL_FAILED` con quel codice (ora anche `90`–`93`), che Weaver tiene fino al prossimo `INSTALL_OMP` o finché omp si trova. I testi per codice di `requirements/ui#system-certificates` ("Failed installer") li implementa la Task «Testi per causa» in `installer_failed_text`; questa Task garantisce solo che il codice arrivi lì com'è oggi.

## Aggiornamento in background (`requirements/tech#omp-setup`, "Updates")

- Il controllo resta solo `omp update --check`, al massimo una volta l'ora. Un solo aggiornamento alla volta in tutta l'app, ripiego compreso.
- Quando `omp update` fallisce o scade, `ompPath` è vuoto e il file omp trovato, con i symlink risolti, sta direttamente in `PI_INSTALL_DIR` o nella cartella predefinita (`%LOCALAPPDATA%\omp`, `~/.local/bin`; non la cartella di bun, non Homebrew) e su Windows non ha un file `.bunx` accanto, Weaver esegue il download GitHub per quella cartella con la versione di omp, come processo figlio nascosto (`/bin/sh -c`; `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command` con `CREATE_NO_WINDOW`), con le variabili di System Certificates, limite di 15 min, nessuna modifica al PATH. Lo script esce `94` senza scaricare quando `tag_name` senza `v` iniziale non è semver più nuovo di quella versione. Vale per ogni aggiornamento.
- Esito: `0` è `omp.UPDATE_ENDED`; `94` è `omp.UPDATE_FAILED` con la ragione di `omp update`; ogni altro codice, o il limite di tempo, è `omp.UPDATE_FAILED` con la ragione di `requirements/ui#system-certificates` ("Failed download of an update") per quel codice, scelta con l'impostazione com'è in quel momento. Il testo lo costruisce la funzione aggiunta dalla Task «Testi per causa» in `crates/core/src/omp/failure.rs`: questa Task le passa l'exit code (o il timeout) e mette il risultato come `reason` di `UpdateFailed`, che la Machine mostra in Ready o dentro il testo di Missing come oggi.
- Il download in background non blocca mai l'avvio, una finestra, la UI o un job in corso; un download fallito lascia l'omp precedente al suo posto e funzionante, senza `.omp.download`.
- Log: ogni download in background a `info` con tag, asset, esito con exit code e durata; un fallimento anche a `warn` con la ragione. Mai il valore del `Path` utente.

## Test (`requirements/quality#omp-setup`)

Script dell'installer per sistema (ufficiale prima, GitHub solo dopo un codice non zero, codice nel marcatore in ogni caso); asset per ogni sistema e variabile del processore, musl, Rosetta, processore sconosciuto; download GitHub contro un server di test locale (stato diverso da 200, pagina HTML, JSON senza asset o digest, file troncato, SHA-256 sbagliato, file che non risponde a `--version`, timeout), ognuno col suo exit code e l'omp precedente intatto; sostituzione su Windows (file rinominato, ripristinato se la verifica fallisce, vecchi file cancellati se liberi); `Path` utente aggiunto una volta sola, non due con maiuscole diverse o `\` finale, e suggerimento stampato su macOS e Linux; ripiego dell'aggiornamento solo dopo il fallimento di `omp update`, solo per omp in `PI_INSTALL_DIR` o cartella predefinita con `ompPath` vuoto e senza `.bunx`, saltato (`94`) se la release non è più nuova, e ogni codice mappato a `omp.UPDATE_ENDED` o `omp.UPDATE_FAILED` con la sua ragione. I test dei testi per codice, in Rust e in Vitest, sono della Task «Testi per causa».

## Documentazione (`requirements/docs#omp-setup`) e Specs

- `README.md`, in `## Behind a corporate proxy`, nuova sottosezione `### When the proxy blocks omp's download`: alcuni proxy bloccano il sito da cui scaricano l'installer ufficiale e `omp update`, e System Certificates lì non aiuta; Weaver scarica allora lo stesso omp dalle release GitHub da solo su macOS, Windows e Linux, nel terminale dopo il fallimento dell'installer ufficiale e in background dopo quello di `omp update`, solo per un omp nella cartella del suo installer e non per uno di un package manager o impostato in `omp path`; dove lo mette (`PI_INSTALL_DIR`, altrimenti `%LOCALAPPDATA%\omp` o `~/.local/bin`), che su Windows aggiunge la cartella al `Path` utente se manca e su macOS e Linux stampa solo come aggiungerla; che il file si installa solo se dimensione e SHA-256 coincidono con GitHub e risponde a `--version`; le cause mostrate con gli exit code `90`–`93`.
- `README.md` `### Where Weaver keeps files`: il download GitHub scrive omp nella cartella del suo installer, fuori dalle cartelle di Weaver, con un file temporaneo `.omp.download` e, su Windows, i file `omp.exe.*.old` di un omp sostituito.
- `CHANGELOG.md` sotto `## [Unreleased]`: in `Added` una riga sul ripiego GitHub per installare e aggiornare omp; in `Changed` una riga sui messaggi di fallimento dell'installer per causa.
- `specs#infrastructure`: la voce omp dice già che, quando il suo canale fallisce, si scarica dalle release GitHub (can1357/oh-my-pi, API REST `releases/latest`); il codice deve corrispondere.
