# Project setup

Putting Weaver in a project folder, keeping up to date what it installs for the agent, keeping Weaver's files out of a shared repository when the developer uses Weaver alone, committing the agent's work feature by feature when the developer wants it, and making sure omp is installed, recent enough, connected to a model provider and able to reach it from behind a corporate proxy.

A folder without a project offers to initialise it. Weaver then creates the `.weaver` folder with an empty Model and installs, for the agent, the skills it carries, the skills generated from the Requirements, the definitions of omp's sub-agents and the instructions of omp's advisor. With an empty Model the developer chooses one of two paths: Start from Scratch, where he writes the setup request and the agent turns it, through an interview, into the setup Proposal that becomes the first Model with the Tasks that build the application; or Import from Code, where the agent describes the code already there as import Proposals. Either way the first Proposals are approved by themselves when they are handed over, because the developer already decided in the interview or the code already exists.

Solo mode lets the developer use Weaver in a git repository where the others do not: while it is on, Weaver's files stay only in this working copy, never go into a commit, and the shared repository sees only the code. It belongs to the working copy, not to the developer: another clone of the same repository starts with it off. Weaver keeps the files out through git's local exclusions, which are never committed, either as whole folders or as only the files Weaver writes there, and puts its exclusions back by itself at every opening of the project. The developer chooses it before initialising, so that Weaver's files are never seen by git, or turns it on and off later in Settings. It needs git; it cannot hide files git already tracks, which Settings lists; and since the files are then versioned nowhere, losing the working copy loses them.

Because the others change the code without updating the Model, Solo mode also offers Merge: Weaver brings another branch into the current one with git, lets the developer resolve the conflicts by hand or with the agent, and once the merge is concluded starts by itself a scan of the whole System, telling the agent which files the merge brought, so that every difference their work opened against the Model becomes a Drift marked as coming from a merge.

Atomic commits, off by default and chosen for each working copy in Settings, makes Weaver commit the code of every History entry the agent writes, one commit per entry, so that the repository's history follows the work feature by feature. It needs git and never pushes.

omp is required: no job and no General conversation starts without it. Weaver finds it, offers to install it and to connect it to a provider through the system terminal, keeps it updated, and checks it again by itself until it answers.

From every project window the developer can open Usage, which shows how much is left of the usage limits of the model providers omp is connected to and when each limit resets. Weaver asks omp for them only when Usage is opened, and never by calling a model.

Behind a corporate proxy that inspects HTTPS traffic, omp fails to install or to reach its provider because it does not trust the proxy's certificate. System Certificates, off by default, makes every omp process Weaver starts trust the certificate authorities the developer's system trusts. Weaver turns it on by itself once when Zscaler is installed, and wherever it shows why omp failed it explains in plain words when a corporate proxy is the likely cause.
